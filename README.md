# Expired Bread

Веб-система хранения электронных документов с автоматическим извлечением
структурированных данных. Пользователь загружает PDF или DOCX, система
извлекает текст, анализирует его через GigaChat, сохраняет проверенные
поля в нормализованном виде и предоставляет поиск по этим полям.

Проект — модульный монолит на Django. Каждый модуль (извлечение текста,
работа с LLM, нормализация, индексация, поиск, оценка качества)
изолирован и тестируется отдельно.

**Версия:** 3.0 (ветка `v3.0`)
**Тесты:** 182, проходят без обращения к сети (`python manage.py test documents`).

## Быстрый старт

```bash
git clone <URL>
cd Expired-Bread

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt

cp .env.example .env             # заполнить GIGACHAT_CREDENTIALS и DJANGO_SECRET_KEY

# сертификат Минцифры — обязателен для GigaChat
mkdir -p certs
curl -k "https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt" \
  -o certs/russian_trusted_root_ca_pem.crt

python manage.py migrate
python manage.py seed_demo       # два пользователя и три документа
python manage.py runserver
```

Открыть http://127.0.0.1:8000/

**Демо-аккаунты:** `demo` / `demo12345` и `other` / `other12345`.
Документы первого не видны второму — это можно показать на защите.

## Возможности

### Загрузка и извлечение
- PDF и DOCX до 20 МБ, проверка расширения **и сигнатуры файла**.
- PyMuPDF для PDF, python-docx для DOCX (включая таблицы).
- Если текстового слоя нет (скан) — ошибка `ExtractionError`,
  срабатывает резервный путь через Vision-модель.
- Тип документа можно указать в форме — тогда классификация моделью
  не вызывается (экономия около 700 токенов на документ).

### AI-обработка
- Классификация (режим «Авто») и извлечение по JSON Schema конкретного типа.
- Один автоматический повтор с текстом ошибки валидации.
- Очистка служебных ключей (`../../../`, `_comment_*`), починка JSON.
- Кэш ответов по хэшу (текст + модель + версия промпта + схема).

### Проверка человеком
- Страница review показывает предупреждения обработки.
- Простые поля правятся обычными inputs, списки и характеристики — JSON-текстом.
- JSON проверяется схемой типа: в базу не попадает структура, с которой
  не умеет работать поиск.
- Сохраняется `data_raw` (ответ модели) и `data` (после правки), поэтому
  считается метрика исправлений: `processing_meta['corrected_fields']`.

### Поиск
- Полнотекстовый поиск по `search_text` (регистронезависимый для кириллицы).
- Фильтры по нормализованным полям: `?f=price:lt:100000&f=ram:gte:16`.
- Операторы: `eq`, `contains`, `lt`, `lte`, `gt`, `gte`.
- Значения фильтров проходят ту же нормализацию, что и данные,
  поэтому `16 ГБ`, `16GB` и `16` ищутся одинаково.
- В поиске участвуют только документы в статусе `ready`.

### Изоляция
- `Document.user`, `DocumentQuerySet.for_user`, все view под `@login_required`.
- Чужой документ по прямому id даёт 404 на любой странице.
- Файлы отдаются только через `document_download` с проверкой владельца;
  раздача `/media/` убрана.

## Архитектура

```
Браузер
   ↓
Django views (тонкие)          documents/views.py
   ↓
Слой сервисов                  documents/services/
   ├── extractors.py           PDF/DOCX → текст
   ├── llm.py                  транспорт к GigaChat (json_chat)
   ├── prompts.py              версионируемые промпты
   ├── pipeline.py             classify → extract → validate
   ├── normalization.py        числа, единицы, даты, ключи
   ├── field_index.py          data → DocumentField
   ├── document_service.py     оркестрация и сохранение
   ├── search_service.py       поиск и фильтры по полям
   └── qa_service.py           Q&A по содержимому
   ↓
Модели                         documents/models.py
   ↓
SQLite + файловая система
```

Отдельно, вне веб-запросов:

```
Документы + эталоны            eval/dataset/
   ↓
evaluation/                    matching → metrics → runner → report
   ↓
Отчёты                         eval/results/<дата>/{summary.json,per_field.csv,errors.csv,report.md}
```

**Правила зависимостей:**
- `views` вызывает только сервисы и не содержит бизнес-логики.
- `schemas` не импортирует Django.
- `pipeline` не знает про БД и HTTP.
- `evaluation` не знает ни про БД, ни про views.
- `llm` не знает про типы документов.

## Типы документов

Единственный источник правды — `documents/schemas/__init__.py` (`REGISTRY`).
Из него берут типы: форма загрузки, фильтр поиска, JSON Schema для модели
и словарь допустимых ключей.

| Тип | Схема | Ключевые поля |
| --- | --- | --- |
| `price_list` | `PriceListData` | `vendor`, `currency`, `items[]` (`name`, `sku`, `price`, `unit`) |
| `specification` | `SpecificationData` | `product_name`, `manufacturer`, `price`, `ram`, `storage`, `characteristics` |
| `technical_document` | `TechnicalDocumentData` | `document_code`, `version`, `sections[]`, `requirements[]` |
| `other` | `BaseDocumentData` | `title`, `description`, `organization`, `date` |

Добавление типа — один файл в `documents/schemas/` и строка в `REGISTRY`.

### Нормализация

Модель возвращает значения **как в документе** («89 990 руб.»), а приведение
к числам делает детерминированный код. Это позволяет тестировать
нормализацию без модели и разделять ошибки на «модель не нашла»
и «код не распознал формат».

| Вид поля | Примеры входа | Результат |
| --- | --- | --- |
| `money` | `89 990 руб.`, `89990 ₽`, `1 299,50` | `89990.0`, `1299.5` + код валюты |
| `memory` | `16 ГБ`, `16GB`, `1 ТБ` | `16.0 GB`, `1000.0 GB` |
| `date` | `15.03.2025`, `2025-03-15`, `15 марта 2025` | ISO-дата + ordinal для сравнений |
| `text` | `ООО «Ромашка»` | нижний регистр, `ё → е`, схлопнутые пробелы |

**Договорённости, зафиксированные в тестах:**
- `1 ТБ = 1000 ГБ` (не 1024).
- `1,500` трактуется как 1500, а `0,500` — как 0.5.
  Неоднозначные случаи стоит проверить табличным тестом при новых данных.

## Поиск по полям

```
/documents/search/?q=ноутбук
/documents/search/?f=price:lt:100000
/documents/search/?f=price:lt:100000&f=ram:gte:16
/documents/search/?q=price:lt:100000&ram:gte:16    # фильтры прямо в q
```

Фильтры соединяются по «И». Ключ проверяется по реестру, оператор —
по белому списку. Неизвестный ключ не ломает поиск: он просто не даёт
совпадений.

**Ограничение:** при комбинировании фильтров по скалярному полю документа
и по позиции списка (`vendor` + `price` в прайс-листе) условия должны
относиться к одной позиции — такая логика (версия 2 поиска) не реализована.

## Оценка качества

Датасет лежит в `eval/dataset/<тип>/<имя>.docx` + `<имя>.truth.json`.
Для каждого документа есть эталон, поэтому метрики считаются автоматически.

```bash
# сколько будет стоить прогон, без вызовов модели
python manage.py evaluate --split dev --dry-run

# прогон на dev-части, два повтора (модель недетерминирована)
python manage.py evaluate --split dev --repeat 2

# быстро, на стратифицированной выборке
python manage.py evaluate --split dev --sample 12

# сравнение двух конфигураций
python manage.py evaluate --config eval/configs/max.json  --out eval/results/max
python manage.py evaluate --config eval/configs/lite.json --out eval/results/lite

# режим «тип из формы» (классификация не вызывается)
python manage.py evaluate --split dev --use-truth-type
```

Разделение dev/test детерминированное: 70 % документов всегда попадают
в dev, 30 % — в test. Настройка промптов идёт на dev, финальные числа
снимаются на test один раз.

### Метрики

- `precision`, `recall`, `F1` по каждому полю; `micro` (по всем значениям)
  и `macro` (среднее по полям).
- Точность классификации и матрица ошибок.
- Доля ошибок нормализации (значение верное, но не разобралось в число).
- Время на документ и расход токенов из `usage`.
- Категории ошибок: `missing`, `wrong_value`, `format`, `hallucination`.

### Отчёты

| Файл | Назначение |
| --- | --- |
| `summary.json` | полная сводка, машиночитаемая |
| `per_field.csv` | метрики по полям (Excel, разделитель `;`) |
| `errors.csv` | каждая ошибка отдельной строкой — главный файл для разбора |
| `report.md` | человекочитаемый отчёт с таблицами |

**Важно:** реальные метрики появляются только после прогона с ключом
GigaChat. Прогон без ключа (например, `--dry-run`) показывает лишь
оценку расхода. Цифры в отчёт для ВКР нужно снимать на test-части.

## Команды управления

| Команда | Назначение |
| --- | --- |
| `python manage.py seed_demo [--reset]` | демо-пользователи и документы |
| `python manage.py rebuild_fields [--all] [--doc ID]` | пересобрать `DocumentField` из `data` |
| `python manage.py evaluate [флаги]` | оценка качества на датасете |
| `python manage.py make_dataset [--per-type N]` | генерация датасета |
| `python manage.py validate_dataset` | проверка эталонов по схемам |

`rebuild_fields` нужно запускать после изменения правил нормализации:
данные в `data` не меняются, а поиск должен увидеть новые значения.

## Безопасность

- `.env`, `certs/`, `media/`, `db.sqlite3`, `.venv/` — в `.gitignore`
  и никогда не коммитились.
- `DJANGO_SECRET_KEY` читается из окружения, в коде только dev-заглушка.
- Загрузка проверяет сигнатуру файла (`%PDF-`, `PK`), а не только расширение.
- Файлы не отдаются напрямую: только через view с проверкой владельца.
- Текст документов не пишется в логи.

**Риски, которые стоит закрыть до публичного доступа:**
- Валидаторы `CommonPasswordValidator` и `UserAttributeSimilarityValidator`
  отключены, чтобы демо-пароли вида `demo12345` проходили регистрацию.
  Перед публикацией их нужно вернуть в `AUTH_PASSWORD_VALIDATORS`.
- В тексте документов возможны инструкции для модели (prompt injection).
  Промпт должен явно требовать считать содержимое документа данными,
  а не командами.
- Регистрация открыта, лимитов на пользователя нет.

## Ограничения и что дальше

1. **Синхронная обработка** (этап 10): 20 МБ PDF и вызов модели внутри
   HTTP-запроса дают таймауты на реальных документах.
2. **Q&A без ранжирования** (этап 9): служебные слова вопроса дают лишние
   совпадения; разбор вопроса в фильтры не реализован.
3. **Схема `resume` осталась в реестре**, хотя по ТЗ резюме (персональные
   данные) из набора убираются. Её надо удалить из `REGISTRY`
   и `TYPE_LABELS`, оставив чтение старых документов.
4. **Фильтры «в пределах одной позиции»** (версия 2 поиска) не реализованы.
5. **Учёт токенов** (этап 25): `usage` собирается в `processing_meta`,
   но сводной команды `usage_report` и дневного лимита нет.
6. **Лимит частоты GigaChat (429).** На бесплатном тарифе запросы ограничены
   по частоте и идут в один поток. SDK делает один повтор, после чего
   документ получает понятное сообщение: подождите минуту и нажмите
   «Повторить обработку». Загружать один и тот же файл несколько раз
   подряд бессмысленно — каждая попытка расходует лимит.
